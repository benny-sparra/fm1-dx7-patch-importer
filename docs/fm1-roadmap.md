# FM1 Editor Development Roadmap

> Working roadmap for evolving the existing M-VAVE FM1 editor/librarian without turning it into a DAW.

## Product direction

The editor should become a better front end for **capabilities that already exist inside the FM1**.

The priorities are:

1. improve correctness and depth of existing editor features
2. document the FM1-specific runtime protocol
3. add a focused editor for the FM1's internal sequencer
4. expose other stock-device capabilities only where they add clear value
5. keep firmware update/recovery work completely outside normal editor functionality

The sequencer feature is intentionally **not** a general MIDI sequencer or DAW.

---

# Phase 0 — Research foundation

## Goal

Make reverse-engineering knowledge durable and safe for both humans and coding agents.

## Deliverables

- `docs/fm1-research.md`
- `docs/fm1-roadmap.md`
- `docs/codex-tasks.md`
- FM1-specific additions to the existing `AGENTS.md`
- protocol confidence labels
- a documented hardware-test procedure

## Exit criteria

- Codex can determine what is known versus speculative without reading chat history.
- Dangerous OTA/loader functionality is clearly marked as excluded.
- New protocol work has an obvious documentation home.

# Phase 1 — Audit and strengthen existing DX7 support

## Goal

Use firmware findings to increase confidence in the editor as it exists today.

## Work

### 1.1 DX7 parameter map audit

Compare every live-editable DX7 parameter against the stock FM1 155-byte edit-buffer mapping.

Check:

- address
- legal range
- encode/decode
- operator ordering
- global parameter ordering
- rename/name handling
- transpose
- parameter-change SysEx generation

### 1.2 SysEx tests

Create/expand fixture-driven tests for:

- single voice data
- 32-voice bank data
- Yamaha checksum
- parameter-change messages
- invalid sizes
- invalid 7-bit values
- malformed SysEx

### 1.3 Editor display semantics

Compare display calculations against the msfa/Dexed-derived synth behaviour where useful.

Candidates:

- envelope graphics
- frequency display
- fixed/ratio interpretation
- velocity/key scaling descriptions
- transpose labels

## Exit criteria

- DX7 live-edit mapping is table-driven and tested.
- No known mismatch with stock firmware remains undocumented.

---

# Phase 2 — Audit current FM1-specific effects

## Goal

Validate and improve features users already have before adding new high-risk protocol code.

## Work

1. Inventory all current effect controls.
2. Record the exact MIDI message generated by each.
3. Locate corresponding firmware behaviour where possible.
4. Assign confidence:
   - Confirmed
   - Likely
   - Needs hardware test
5. Identify any useful stock effect parameter not currently exposed.
6. Add tests for known encodings.
7. Improve MIDI monitor labelling for FM1 effect messages where possible.

## Constraints

- Do not expose raw DSP coefficients as user parameters.
- Do not infer user-editable parameters from arbitrary internal state.
- Do not use unknown vendor commands.

## Exit criteria

- Every shipped effect control has documented protocol provenance.
- Any proposed new effect control has a safe normal runtime path.

# Phase 3 — Vendor runtime protocol investigation

## Goal

Determine whether the FM1's vendor-specific command transport exposes safe runtime operations needed for sequencer editing.

## Work

### 3.1 Build command catalogue

Track:

```text
command
subcommand
payload format
reply format
transport
observed stock action
confidence
safe runtime?
hardware tested?
```

### 3.2 Capture normal device behaviour

Using the current MIDI monitor and external inspection where needed:

- switch arp/seq mode
- select sequence bank
- select pattern
- change tempo
- change swing
- record one note
- record multiple notes
- clear pattern
- save pattern if the stock UI offers it

Change one value at a time.

### 3.3 Classify command families

Separate:

- ordinary Yamaha DX7 SysEx
- FM1 normal runtime commands
- BLE app/control messages
- vendor/syscmd commands
- OTA/update/loader traffic

### 3.4 Safety gate

No command may be added to production write code unless:

- its purpose is understood
- it is not part of OTA/loader entry
- its payload bounds are validated
- it has been observed or safely reproduced on hardware
- failure behaviour is understood sufficiently for normal use

## Exit criteria

At least one safe method is known for one of:

- reading sequence state, or
- setting sequence state through stock runtime mechanisms.

If no safe direct transport exists, document that conclusion and investigate whether controlled stock recording input can satisfy the editor's goals.

## Outcome — closed 2026-09-06 (negative for direct transport)

**No safe direct sequencer transport was found.** The V15 capture set in
[`sequencer-fixtures/V15/`](sequencer-fixtures/V15/) covers clear, record, playback, velocity, gate,
step length, pattern separation, save, and power cycle. Across every one of those controlled stock
sequencer actions, **no SysEx or vendor frame was observed in either direction**. The staged
`F0 35 59 … F7` transport remains recognised but carries no known sequencer command ID, payload,
reply, or checksum, and stays excluded under 3.4.

The Phase 3 exit criteria are therefore **not** met for a direct read or write path. Per the exit
clause, the fallback is now the live track: controlled stock recording input, plus observation of
the device's own playback output, is the only evidenced route to sequencer functionality.

### What the fallback rests on

Each of these is Confirmed observable V15 behaviour in the committed fixture set:

| Behaviour                                                        | Evidence                                                                 |
| ---------------------------------------------------------------- | ------------------------------------------------------------------------ |
| The FM1 records from inbound standard MIDI Note On/Off           | Paired host notes 60/64/65 replayed with pitch and velocity kept         |
| The FM1 emits its playback as outbound standard MIDI Note On/Off | Ordered playback passes captured with measurable period and gate         |
| Gate is global, not stored per step                              | 180 ms and 299 ms holds both replayed at 131-134 ms; Gate 50% gave 83 ms |
| Step `1..16` is loop length, not a record-position selector      | Step 16 recurrence at 2,665 ms; Step 1 gives one note per step           |

The third row is the one that makes a host implementation practical: because the device quantises
what it records and applies one global gate, host transmission does not need sample-accurate
timing. Web MIDI scheduling jitter is not a blocker for this path.

### What the fallback does not resolve

Unchanged and still Unknown: arming record mode from the host, selecting pattern or chain, setting
step length, gate, rate, tempo, swing, or transpose, triggering the stock `SAVE`, and any readback
of raw record state. All of these remain stock-UI-only operations. The editor must not claim to
perform them and must not present the V13 32-byte record layout as V15 truth.

The two behaviours that gated the fallback's design were resolved by SEQ-001B on 2026-09-17: a host
can insert rests by sending a Note On with velocity 0, and two identical successive notes occupy two
distinct steps. Recording also always starts at step 1 and overwrites forward, leaving later steps
intact. A host-authored pattern can therefore express pitch, velocity, rests, repeats, and position.
See §5.8 of [`fm1-research.md`](fm1-research.md).

### Consequences for later phases

- Phase 4 may proceed for a **behavioural** model built on confirmed V15 playback observations. It
  must not be built on the V13 record hypothesis, which remains firmware evidence without hardware
  corroboration. SEQ-002 and SEQ-003 stay blocked.
- Phase 6 gains a parallel read track: reconstruct the pattern from observed playback rather than
  from a request/reply. See SEQ-OBS-001 and SEQ-OBS-002.
- Phase 7 gains a parallel write track: transmit a pattern as recorded input while the user has
  armed the device by hand. See SEQ-REC-001 and SEQ-REC-002.

Direct-transport work is not abandoned, only unfunded by evidence. If a future firmware or a lawful
capture of the vendor BLE application produces a repeatable request/reply, Phase 3 reopens and the
SEQ-READ / SEQ-WRITE tasks resume ahead of the fallback.

# Phase 4 — Sequencer domain model and codec

## Goal

Model the FM1 sequence independently of the UI and independently of device transport.

> **Phase 3 closure applies.** Model the sequence from Confirmed observable V15 behaviour — ordered
> steps, per-step pitch and velocity, loop length `1..16`, and global gate. Do not model the V13
> 32-byte record; that layout is firmware evidence without hardware corroboration, and SEQ-002 and
> SEQ-003 remain blocked.

## Work

Create a TypeScript model for the documented sequence representation.

Responsibilities:

- parse a verified 32-byte pattern record
- encode a pattern record
- represent rests
- represent note/velocity pairs
- enforce maximum step/note count
- validate valid-count and flags
- preserve unknown flag bits during round trips where appropriate
- reject malformed records

## Important rule

Unknown bytes/bits should not be silently zeroed if that could destroy stock-device state.

Prefer round-trip preservation.

## Tests

Fixture tests should include:

- empty pattern
- one-note pattern
- maximum-length pattern
- rests
- extreme valid note values
- velocity boundaries
- unknown flags retained
- invalid lengths rejected
- encode(decode(bytes)) round trip

## Exit criteria

The codec is independently tested without MIDI or React.

# Phase 5 — Sequencer UI using mock data

## Goal

Build the user experience without depending on unfinished hardware communication.

## Proposed route/navigation

Add Sequencer as a peer-level FM1 feature rather than hiding it inside DX7 voice editing.

For example:

```text
Library
Voice Editor
Sequencer
```

Fit this into the existing navigation architecture rather than forcing this exact structure.

## Initial UI

- bank selector
- pattern selector
- compact grid / piano-roll-like editor
- note/rest editing
- velocity editing
- valid length
- clear/reset pattern
- unsaved-change handling
- disabled/read-only states
- narrow viewport behaviour
- keyboard accessibility

Optional only if supported by verified domain data:

- tempo
- gate
- swing

## Explicitly omit

- tracks
- clips
- MIDI file import/export
- song arrangement
- audio engine
- automation
- plugins
- mixer
- DAW-style transport

## Exit criteria

A complete sequence can be edited using in-memory/mock data with strong tests and no hardware dependency.

# Phase 6 — Hardware read support

## Goal

Populate the Sequencer UI from the physical FM1.

> **Phase 3 closure applies.** The request/reply flow below has no evidenced transport and is
> blocked. The available read track is observation: listen to the device's own playback output and
> reconstruct the pattern from it. See SEQ-OBS-001 and SEQ-OBS-002. The requirements below still
> govern that track, except that "malformed response rejection" becomes "reject an incomplete or
> ambiguous observation rather than displaying a partial pattern as fact".

## Preferred flow

```text
user connects FM1
user opens Sequencer
user requests/refreshes current pattern
browser receives safe runtime response
codec validates it
UI displays sequence
```

## Requirements

- explicit loading state
- timeout/failure handling
- malformed response rejection
- no write on read failure
- no fallback that silently replaces unknown device state
- reconnection handling
- cancellation/unmount handling consistent with existing MIDI architecture

## Exit criteria

The editor can reliably show a sequence read from hardware without altering it.

---

# Phase 7 — Hardware write support

## Goal

Safely edit the FM1's internal sequence.

> **Phase 3 closure applies.** The write operations below have no evidenced transport and are
> blocked. The available write track is controlled stock recording input: the user arms record mode
> by hand, and the editor transmits a pattern as ordinary Note On/Off. See SEQ-REC-001 and
> SEQ-REC-002. That track cannot update one note in place, cannot select a pattern, and cannot save;
> it replaces the whole recorded sequence, so 7.3 persistence semantics matter more, not less.

## Staged progression

### 7.1 First write experiment

Implement the smallest reversible verified operation.

Examples, depending on protocol:

- update one note
- update one velocity
- send one complete pattern to a temporary/current buffer

### 7.2 Expand fields

Only after repeatability:

- rests
- length
- velocities
- flags with understood meaning
- timing
- swing

### 7.3 Persistence semantics

Determine whether:

- write is temporary
- write changes RAM only
- device auto-saves
- an explicit stock save action is required

The editor must tell the user what will persist.

## Safety

- require validated ranges
- never send unknown flag values generated from scratch
- preserve unknown state where possible
- rate-limit/debounce live writes if necessary
- retain a known-good local copy before changing the device
- provide a revert/resend workflow where feasible

## Exit criteria

Normal sequencer editing is reliable and does not interact with OTA/loader mechanisms.

# Phase 8 — Local sequence library, if useful

## Goal

Allow useful reuse without creating another large subsystem.

Possible features:

- save FM1 sequence locally
- duplicate
- rename
- export/import a small editor-specific format
- associate a sequence with a patch as metadata

## Architectural rule

Keep a DX7 voice and an FM1 sequence as separate domain objects.

A future "FM1 setup" can reference:

```text
voice
effects
sequence
performance settings
```

but should not corrupt DX7 compatibility by embedding FM1 data in voice SysEx.

# Phase 9 — Arpeggiator and performance settings

After the sequencer protocol work proves safe, consider:

- arp mode
- octave expansion
- timing/gate
- transpose
- controller diagnostics
- other confirmed stock settings

Only expose settings with a clearly understood runtime path.

# Parked — Slot-addressed voice-bank write

## Status

Parked research. Nothing here is scheduled, and no production code may send these messages.

## Why it is listed

A third-party capture of M-VAVE's updater preset restore
([research notes 6.3](fm1-research.md#63-updater-preset-restore-over-manufacturer-id-00-32)) shows a
host sending 128 voices in 16 acknowledged `00 32` blocks, each with an explicit target slot. If safe,
that would let the editor write a bank to a chosen FM1 bank and confirm delivery, rather than rely on
a standard DX7 bank dump that the user places on the hardware.

## Blocking evidence

- The four setup messages are published but unclassified; only the byte that varies between them is identified.
- The traffic comes from an updater build that downgrades firmware, so it is Dangerous / excluded
  until shown to be separate from the update, loader, OTA and flash-erase paths.
- Persistence, checksum, interruption and error behaviour are unknown.
- There is no committed fixture and no repeat on stock v15 hardware.

## Unblock order

1. Obtain a complete, redacted capture as a fixture, with firmware version recorded before and after.
2. Classify every message against research sections 6 and 9.
3. Add a fixture-based decoder test for the payload only. It must not include a transmitter.
4. Get project approval before any hardware experiment. Stock DX7 bank dumps remain the supported write
   path until then.

# Definition of done for protocol features

A protocol-backed feature is not done until:

- protocol is documented
- confidence level is recorded
- codec/range validation exists
- unit tests exist
- hardware test result is recorded where applicable
- MIDI monitor can make the exchange understandable where practical
- errors are recoverable
- no update/loader command path is reachable
- `npm run check` passes
- README/user help is updated where needed

This order gives useful improvements early while keeping the more exciting sequencer work moving forward.

The byte-level track — SEQ-002, SEQ-003, SEQ-READ-\*, SEQ-WRITE-\* — is not in this order because it
is blocked on evidence that does not exist yet. It resumes ahead of the recording path if a lawful
capture ever proves a safe request/reply.
